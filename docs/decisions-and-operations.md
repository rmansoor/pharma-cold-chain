# Decisions, tradeoffs, operations and verification

## Architecture decision records

| ADR | Decision | Rationale | Tradeoff / revisit trigger |
|---|---|---|---|
| 001 | Java 17 and Spark SQL | Consistent with the prior Java/Spark project and strong temporal batch APIs | More verbose than Python; SQL view names currently assume one evaluation per session |
| 002 | Kafka transport plus Delta storage | Separate event ingestion from durable, revisable evidence | Additional persisted copies and operational surfaces |
| 003 | Delta 3.3.3 with Spark 3.5.7 / Scala 2.12 | Keep a compatible Spark 3.5 dependency line | Versions are pinned, not claimed to be newest; upgrades need compatibility tests |
| 004 | Preserve Bronze before interpretation | Late corrections and investigations need original evidence | Storage retention and restricted access must be planned |
| 005 | Full retained-history recomputation first | Simple correction semantics and a testable baseline | Superseded for Gold by ADR 022 (SID-23); Bronze parsing and Silver are still rebuilt in full |
| 006 | Union intervals before summing | Avoid inflated duration from overlapping evidence | Sorting/window operations and temporal joins are expensive |
| 007 | Manifest-last Gold publication | Consumers see only complete product snapshots | Requires reader discipline; no general multi-table transaction |
| 008 | Missing coverage is insufficient data | Avoid treating a sensor outage as normal conditions | More quality-review workload and need for explicit resolution |
| 009 | Single local writer and volumes | Repeatable demonstration with minimal infrastructure | No HA, shared cloud storage, multiple writers or disaster recovery |
| 010 | Human quality authority | Pipeline explains evidence and prioritizes review | Approval and disposition workflow must be integrated separately |
| 011 | Latest approval wins inside a specification overlap; a tie is unresolved | Deterministic, documented precedence that lets a newly approved specification supersede part of an older one without editing it; ties are reported instead of guessed | A mistaken later approval wins until revised; needs an approval workflow with approver identity |
| 012 | Measurement quality limits the conclusion, not the exposure | Uncalibrated or uncertain measurements cannot support NO_OBSERVED_EXCURSION, but an out-of-range value always counts | More INSUFFICIENT_DATA; requires calibration feeds for every sensor |
| 013 | Synthetic thresholds need an explicit deployment flag | Demo thresholds must never drive a real assessment by accident | The flag is per deployment, not per product or user |
| 014 | Every Gold duration is a persisted interval set; derived durations are interval differences | An analyst can see which seconds make up each number, and the numbers agree with the intervals by construction instead of by subtracting totals | More rows per snapshot; the elementary-window join grows with boundary count |
| 015 | Evidence names the exact current revision (eventId, revision, payloadHash, Bronze coordinates) and is kept per snapshot | A superseded assessment can still be traced to what it was computed from; a payload hash distinguishes content even if a source reuses a revision | gold/exposure_intervals grows with snapshots × intervals and has no retention policy; earlier revisions are found through Bronze, not copied |
| 016 | Outcomes and flags come from one versioned policy definition, persisted beside Gold | Code and the published definition cannot disagree; every row names the policyVersion it was assessed under | A policy change needs a new version and a new row; old rows keep the old version |
| 017 | Data-quality flags never change the outcome | A reviewer sees missing, ambiguous or stale evidence on every outcome, including QUALITY_REVIEW, and outcomes stay explained by reasons alone | Some flags repeat a reason (MISSING_COVERAGE); consumers must not treat a flag as an outcome |
| 018 | Mixed specification periods use the smallest allowance for the cumulative excursion | Conservative: a change of specification never widens the allowance for time already spent under a stricter one | May review a unit that each specification alone would accept; excursionBySpecification shows the split. Needs a validated stability model to replace |
| 019 | Spark adaptive execution is off in every session | Structured Streaming disables it inside foreachBatch; with it on, tests passed plans the streaming job could not analyze | Tests are slower (sort-merge instead of runtime broadcast joins); a performance story should restore speed explicitly |
| 020 | A retry deletes rows of its snapshot that have no manifest; a replay after the manifest writes nothing | The published snapshot is exactly one attempt's output, and published rows are never rewritten | A long Gold write is repeated in full after a crash |
| 021 | Manifest digests cover content only, and lineage changes are refused | A retry can be proven equal to a clean run, and a checkpoint reset cannot overwrite published snapshot IDs | Recovering from a deliberate checkpoint reset needs a new data namespace |
| 022 | Gold is recomputed only for affected units, judged by entity on both the old and new value of each changed event | Correction cost follows the units a change touches, not the size of history; an over-approximation is safe because recomputation is exact | Entity-level, not time-level: a change outside a unit's intervals still recomputes it. Bronze parsing and Silver still scan all history |
| 023 | Gold history, intervals and segments are change logs resolved per snapshot, with tombstones; writes are appends | A correction writes rows only for what changed, and appends never scan the table | Readers must resolve state through Snapshots; history grows by changed rows, with no compaction policy yet |
| 024 | dataAsOf-dependent fields (inventory age, STALE_INVENTORY) are derived when a snapshot is read | Otherwise any newer event anywhere would change every unit's row and defeat incremental recomputation | Those fields are not in stored rows or assessmentHash; readers must use Snapshots or Policy.asOf |
| 025 | The canonical row keeps the first arrival among identical copies of the current revision | A retry changes nothing, not even the source coordinates evidence cites | The coordinates name the first copy, not the latest |
| 026 | `Replay` rebuilds Gold from a namespace's Bronze into a new, empty namespace with its own lineage, and compares digests | The full reference for incremental results, and the supported way to rebuild under a new checkpoint lineage | A replay costs a full recomputation; it never writes to the source. It uses the configuration recorded in the source manifest |
| 027 | A container shipment line ships the units resolved into the container at the dispatch instant | Matches how shipper boxes are dispatched, and reuses lineage instead of asking sources to list every unit | A unit in an ambiguous chain at dispatch is not listed; there is no receipt confirmation |
| 028 | Every query takes a scope, and an explicit out-of-scope filter is refused | A recipient sees only its own units and shipments, and a refusal is distinguishable from an empty result | Authentication is not implemented; the deployment must map callers to scopes (CC-15) |
| 029 | Query cursors pin one committed snapshot and are bound to the query and scope | Paging is consistent while new snapshots are published, and a cursor cannot be replayed under another scope | A long paging session keeps reading an older snapshot until the caller starts a new query |
| 030 | Review items are Gold rows of their snapshot (a transactional outbox), relayed to Kafka only after the manifest | An item exists exactly when its assessment is published; no distributed transaction between Delta and Kafka is needed | Delivery is at least once: a crash after Kafka accepted a snapshot and before the relay recorded it resends the snapshot |
| 031 | Consumers deduplicate on deliveryId (one per assessment revision) and apply an item only when its snapshotId is newer than the case's | Redelivery, consumer replay and late older revisions change nothing, without exactly-once Kafka transactions | A consumer must keep deliveryIds for as long as redelivery is possible; the case store keeps them all |

## Local operating runbook

Requirements: Docker Compose v2, network access for the first image and dependency download, and at least 4 GB of Docker memory (6 GB recommended when other stacks share it).

| Component | Version (pinned) | Measured memory (idle, after demo) | Host port |
|---|---|---|---|
| Kafka (KRaft, single broker) | apache/kafka:3.9.1 | ~330 MiB | 29092 |
| Pipeline (Spark 3.5.7 local[2], Delta 3.3.3) | eclipse-temurin:17.0.21_9-jre, heap capped at 2 GiB | ~1.6 GiB | 4041 (Spark UI) |
| Case store (same image, Spark streaming consumer) | as the pipeline | not yet measured | none |
| Build image | maven:3.9.9-eclipse-temurin-17 | build only | none |

Measured on 2026-11-05 with Docker Desktop (12 CPUs, 7.7 GiB). The pipeline image is 911 MB and the Kafka image 626 MB; after the demo, Kafka data is ~360 MB (mostly preallocated segments) and lake data is ~220 KB. Peak memory under load has not been measured. Host ports were chosen so they don't conflict with the fraud demo (19092, 4040).

Run from project root:

```sh
docker compose up -d --build pipeline cases
docker compose --profile demo run --rm simulator
docker compose --profile demo run --rm verify
docker compose --profile demo run --rm verify io.coldchain.Replay /data /tmp/replay   # full recomputation in an isolated namespace; MATCH or exit 1
docker compose --profile demo run --rm verify io.coldchain.Query --scope investigator --recipient HOSPITAL-DEMO   # affected units shipped there
docker compose --profile demo run --rm verify io.coldchain.Query --scope recipient:HOSPITAL-DEMO --limit 1   # the hospital's own view; repeat with --cursor <NEXT>
```

Host broker localhost:29092; Spark UI localhost:4041. Internal Kafka kafka:9092. DATA_DIR defaults to /data; pipeline-data persists Bronze, Silver, Gold and checkpoints. The simulator pauses 40 seconds between initial and corrected assignments. The verifier waits up to `VERIFY_TIMEOUT_SECONDS` (600 by default) for the corrected snapshot, and the crash and restart checks wait up to 10 minutes per batch: on a shared CI runner one demo batch has taken 97–134 s. This is a demo timing assumption, not a reliable synchronization contract; the hardened verifier/simulator story replaces it with committed-snapshot acknowledgement and run-scoped IDs.

```sh
mvn -s maven-settings.xml -B test
mvn -s maven-settings.xml -B test -Dtest=ScaleBenchmark -Dbench=true -Dcontainers=400 -Dunits=10 -Dhours=48   # correction latency
export ALLOW_SYNTHETIC_SPECS=true   # demo only: lets the pipeline use the simulator's synthetic thresholds
docker compose logs -f pipeline
docker compose restart pipeline
docker compose down
scripts/restart-check.sh   # after the demo: full down/up, then one new event
scripts/crash-check.sh     # disposable project: crash after Bronze, before a Gold manifest and after a relay; recover each
```

`scripts/restart-check.sh [project]` checks that persisted state survives a full `down`/`up`: counts must be unchanged with no new input, and one new event must add exactly one Bronze row and continue the snapshot sequence. CI (`.github/workflows/ci.yml`) runs the Spark tests, a gitleaks scan of source and history, then a fresh Compose deployment, the demo and the restart check on every pull request and every push to main. Images contain only the application jar, runtime libraries and the OS CA bundle; no credentials are used or stored.

**Review items.** The pipeline relays each committed snapshot's items to `coldchain.review-items` and records it in `outbox/relayed`; the `cases` service keeps the reviewers' case store in the case-data volume (CASES_DIR=/cases). `io.coldchain.Inspect` prints `outbox` (committed items), `relayed`, `pending` (committed snapshots not yet relayed), `notifications`, `deliveries` and `openCases`. Triage:
- `pending` stays above 0: the broker is unreachable or rejecting writes; the log shows `RELAY DEFERRED` with the cause. Items are retried every 10 s and after every batch; nothing is lost while the outbox is retained.
- `deliveries` below `relayed`: the case store is behind or stopped (`docker compose logs cases`).
- To rebuild the case store (lost volume, or behind by more than the 7-day topic retention): stop `cases`, delete the case-data volume, delete all rows of `outbox/relayed` so the relay sends every committed item again, and start `cases`. The case store ends with each unit's newest item; notification times are the times of the rebuild.

`docker compose down` preserves named volumes. `docker compose down -v` deliberately destroys this project's events, lake data and checkpoints; use only for a deliberate disposable-demo reset. macOS Docker may need /Applications/Docker.app/Contents/Resources/bin on PATH. JDK 17 is used in containers and for the local build. The application has no automated retention purge.

## Failure and recovery matrix

| Failure | Expected recovery | Verification required |
|---|---|---|
| Repeated Kafka payload at new offset | Bronze retains both; canonical ID/revision collapses retries | Assert exposure and coverage remain 600 seconds |
| Invalid JSON or contract | Bronze retains input; quarantine records reason codes, coordinates and raw evidence | Demo verifier asserts MALFORMED_JSON; SilverTest asserts resolution by a corrected revision |
| Higher revision arrives late | Supersede prior canonical event and rebuild assessments | Assert old product loses exposure, new product gains it |
| Sensor in two containers or two custodians at once | Report the anomaly; leave both events out; the unit shows missing coverage or missing custody | TimelineTest asserts the anomaly and its effect |
| Assignment corrected | List units on both the former and revised side in mapping_invalidations; recompute Gold | Demo verifier and TimelineTest assert FORMER UNIT-A, UNIT-D and REVISED UNIT-B |
| Duplicate reading under another ID, or two sensors in one container | Each interval set is merged before summing; every reading stays listed as a source | ExposureTest asserts 600 s, not 1200 or 1500, with all three readings in the excursion interval's sources |
| Readings stop inside a placement | The unmeasured time is a MISSING interval explained by the membership that expected the unit | ExposureTest asserts the gap and its source; the demo verifier asserts UNIT-A's 600 s MISSING interval after the correction |
| Ambiguous lineage, assignment, custody or specification | Report the flag on every affected unit whatever the outcome; leave the ambiguous source out of exposure | PolicyTest asserts each flag and the unchanged outcome |
| Inventory older than 24 h or recorded before the unit last moved | STALE_INVENTORY; location is still shown as latest known | PolicyTest asserts the exact age boundary and the moved case |
| Overlapping specifications | Latest approval applies; a tie leaves the window without a specification; both listed in specification_overlaps | MeasurementTest asserts both resolutions and the Gold effect |
| Sensor calibration expired or reading near a limit | Gold reports uncalibratedSeconds or possibleExcursionSeconds and the assessment is INSUFFICIENT_DATA | MeasurementTest asserts each reason |
| Contradictory or cyclic packaging | Report the anomaly; leave the memberships out of lineage; the unit shows missing coverage | LineageTest asserts each anomaly and INSUFFICIENT_DATA |
| Conflicting same revision | Block ID; open a conflict case listing every variant; a higher revision resolves it; case_log records both | Demo verifier asserts inventory-C opened then resolved; SilverTest asserts no arbitrary winner |
| Crash after Bronze | Resume batch using checkpoint; source-coordinate MERGE idempotent | scripts/crash-check.sh (run in CI) |
| Crash after interval or history write, before manifest | Readers keep the previous snapshot; the retry deletes the unpublished rows, rewrites them and commits | PublicationTest (both points, with a planted stale row); scripts/crash-check.sh halts after history in Compose |
| Crash after manifest, before Spark records the batch | The replay finds the manifest and writes nothing to Gold | PublicationTest asserts unchanged Delta versions |
| Expired Kafka offsets | failOnDataLoss=true fails visibly | Backfill plan and broker retention test |
| Lost local volumes | Demo has no replicated recovery | Backups/shared storage are production work |
| Reader starts while the first Gold commit is being written | Snapshots.exists lists the Delta log instead of trusting DeltaTable.isDeltaTable's cached answer | PublicationTest copies a commit in from outside the JVM; CI starts the verifier before the first commit |
| Late correction of an assignment, membership, specification, reading, custody or inventory | Recompute only the affected units, judged on old and new values; others keep their rows | IncrementalTest asserts the recomputed units and full-recomputation digests after each correction kind |
| Rule, policy, code or configuration change | The next snapshot is FULL, with the reason in the manifest | IncrementalTest asserts CONFIGURATION_CHANGED |
| Incremental result in doubt | `Replay` recomputes the same Bronze in full into an isolated namespace and compares digests | IncrementalTest; CI runs Replay after the demo and fails on MISMATCH |
| Snapshot published while a caller pages through results | Later pages read the snapshot the first page pinned | QueryTest publishes a correction between pages and compares with the pinned snapshot |
| Caller asks outside its scope | AccessDenied for an out-of-scope recipient, location or unit's evidence | QueryTest and the demo verifier |
| Crash after review items are written, before the manifest | The items are uncommitted: never relayed, and replaced by the retry | AlertTest |
| Crash after Kafka accepted a snapshot's items, before the relay recorded it | The restart (or the 10 s timer) resends the snapshot; consumers ignore known deliveryIds | AlertTest; scripts/crash-check.sh halts after the relay in Compose |
| Kafka unavailable to the relay | The batch still publishes; RELAY DEFERRED; items stay pending and are retried | Inspect `pending`; AlertTest defers a relay and sends it later |
| Case store crashes or restarts mid-batch | Its checkpoint reprocesses the batch; both writes are idempotent | AlertTest stops it between its writes; scripts/crash-check.sh kills it |
| Older revision of an item delivered after a newer one | The case keeps the newer one; the notification log records both once | AlertTest |
| Checkpoint reset with retained Gold | Publication refused: gold/commits names another lineage; use a new data namespace | PublicationTest asserts the refusal and that nothing was written |

## Security and governance

Demo inputs are synthetic and contain no patient records. Production should minimize personal data: inventory location and lot traceability often suffice without patient identity. Apply TLS/SASL and least-privilege Kafka ACLs, scoped storage permissions, encrypted storage, secret management and access audit. Separate operator replay permissions from source-data deletion and quality approval. Define domain-approved retention and deletion policies rather than assuming indefinite storage. Controls and validated regulatory alignment require a separate review; this prototype does not establish compliance.

## Observability and service objectives

Track Kafka backlog, micro-batch runtime, publication age, quarantine/conflict counts, coverage gaps, changed-assessment counts, temporal fanout, Delta file counts, disk consumption and checkpoint health. Alert on stalled commit manifests even if Spark remains running. Record source offsets and code/rule versions with each published snapshot in the target design.

Candidate engineering objectives to negotiate: publication within 60 seconds at the agreed load, correction within two minutes of receipt, no duplicate product/snapshot keys, complete lineage for every review item and documented recovery point/time. These are proposed acceptance targets, not measured performance or commitments.

## Test strategy and current evidence

Six local Spark tests pass (2026-11-05, SID-13): revision changes exposure A->B while duplicates remain bounded; overlapping readings use interval union; malformed/conflicting contracts are excluded; every published contract example is valid; 22 single-rule violations (blank identifiers, revision, kind/status enums, interval bounds, subsecond bounds, future readings, NaN/infinite values, wrong topic, malformed JSON) are rejected; reformatted retries do not conflict while a changed payload or a reused ID across kinds does. Real-broker evidence (2026-11-05, SID-14): two runs from empty volumes passed the demo verifier and the restart check. CI repeats both on every change. Fault injection (2026-11-05, SID-15): scripts/crash-check.sh halts the pipeline after the Bronze commit of batch 0 (5 Bronze rows, no Gold commit). After restart, batch 0 is replayed and committed as snapshot 0 with exactly 5 Bronze rows. BronzeTest adds 3 Spark tests for provenance and idempotency, bringing the total to 9. Crashes at other points were not injected yet (SID-22 adds the Gold interval and history points; the remaining points belong to SID-28). Silver cases (2026-11-06, SID-16): every contract violation now maps to one reason code (26 cases plus wrong topic and a multi-fault record). SilverTest adds 3 Spark tests for quarantine evidence, conflict cases and the case log, bringing the total to 12. A mutation that let the latest disputed revision count as resolved fails 4 tests. The demo now sends a conflicting inventory-C pair and a revision 2 correction, and the verifier requires the case log to show it opened and then resolved. Packaging lineage (2026-11-06, SID-17): LineageTest adds 3 Spark tests, bringing the total to 15. Across a pallet split at 12:10, exactly U1-U4 are in container X in the minute before and exactly U1-U2 from 12:10. A hot reading in X after the split puts only U1 and U2 under review. Merge and repack move units between containers at the right instant. Contradictory parents, level mismatches and cycles are reported and kept out of lineage, while the affected unit shows missing coverage. Mutations that close the intervals or stop excluding anomalous memberships fail 3 and 1 tests. The demo adds UNIT-D in a carton on a pallet in BOX-A, and the verifier requires it to move with UNIT-A after the correction. Assignments and custody (2026-11-06, SID-18): TimelineTest adds 3 Spark tests, bringing the total to 18. They cover a correction that arrives before the revision it replaces, a retry and a non-mapping revision, one sensor in two containers versus two sensors in one, and a custody handover, gap and overlap. Mutations that drop the former side of an invalidation or keep contradictory assignments fail 1 and 2 tests. The demo verifier also requires the correction's invalidations and the custody figures. Specifications and measurement quality (2026-11-08, SID-19): MeasurementTest adds 5 Spark tests, bringing the total to 23. They cover a later approval superseding part of an earlier specification and a tie left unresolved; synthetic thresholds used only when allowed; °C, °F and K readings normalized to the same value and exposure; a calibrated cool reading as the only NO_OBSERVED_EXCURSION, with a near-limit reading, an expired calibration and an uncalibrated hot reading; and a point reading that covers no time and fills no sampling gap, yet puts the unit under review when out of range. ModelTest adds 10 contract cases (units, calibration, point intervals, the synthetic flag). Mutations that resolve a tie arbitrarily, ignore the synthetic flag, ignore uncertainty or hold a point reading for 60 s each fail 1 test. The demo marks its thresholds synthetic, adds a calibration for SENSOR-1, and the verifier requires both to be reported. Exposure intervals (2026-11-08, SID-20): ExposureTest adds 5 Spark tests, bringing the total to 28. They cover half-open boundaries (touching readings form one interval; a reading or point at the placement's end instant adds nothing), a duplicate under another ID and a second overlapping sensor counted once, gaps persisted as MISSING, UNSPECIFIED and MISSING_CUSTODY intervals with their sources, an assignment split at 12:05 that keeps the 600 s total and shows each side's revision, and evidence that names revision 3 of a reading with its payload hash and offset. Every case checks that each Gold duration equals the sum of its persisted, disjoint intervals. Mutations that drop the union, close the segment boundary, skip the gap subtraction or count touching intervals as sources fail 3, 1, 3 and 1 tests. The existing 23 tests pass unchanged, so no Gold number moved. The demo verifier also requires UNIT-B's excursion interval to cite assignment revision 2 and the earlier snapshot's UNIT-A interval to cite revision 1. The first Compose run found a defect the Spark tests did not: joining a checkpointed view back to the view it was checkpointed from failed analysis in the streaming batch, because both kept the same column IDs. The joined-back side is now re-aliased; it could not be reproduced outside the streaming run, so the CI Compose job is its regression check. (SID-21 found the cause: Structured Streaming turns adaptive execution off inside foreachBatch. Sessions now disable it everywhere, and the Spark tests reproduce this class of failure.) Assessment policy (2026-11-09, SID-21): PolicyTest adds 6 Spark tests, bringing the total to 34. They cover exact thresholds (60 s against a 60 s allowance is within it and 61 s is not; 8.0 °C at the limit is in range but within uncertainty; 7.5 °C is exactly outside the margin; inventory exactly 24 h old is current and one second older is stale), partial coverage on both an insufficient and a reviewed unit, mixed specification periods with the per-specification breakdown, each ambiguity flag beside an unchanged outcome, inventory recorded before the unit moved, and outcomes that match the persisted policy, none of which implies release. Mutations that make the allowance or the inventory age non-strict, use the largest allowance, or flag lineage only on the unit's own membership each fail 1 test. The first Compose run failed with conflicting join references that the tests did not show; disabling adaptive execution in tests reproduced it in 24 tests, and aliasing each view before the final join fixed it. The demo verifier also requires the persisted policy, policyVersion on every row, UNIT-B reviewed with only MISSING_CUSTODY flagged, and UNIT-D with MISSING_COVERAGE and UNKNOWN_INVENTORY. Gold publication (2026-11-09, SID-22): PublicationTest adds 3 Spark tests, bringing the total to 37. They run the real Pipeline.process against temporary lakes. Stopping batch 1 after its interval write and after its history write leaves readers on snapshot 0 with its digest unchanged; a stale uncommitted row planted before the retry is removed; the retried snapshot's assessments digest, evidence digest, revision count and product count equal a clean run's; replaying the batch after its manifest leaves every Gold table at the same Delta version; and a batch from another checkpoint lineage is refused with nothing written. The manifest records the lineage and run IDs, code, rule and policy versions, the high-watermark of every topic partition, the Delta version of every table read and written, and an evidence digest the test recomputes from the pinned assessments. scripts/crash-check.sh adds a second phase that halts after the Gold history write: readers still see snapshot 0, and the restart publishes snapshot 1 once with no duplicate rows. The demo verifier reads only through the pinned snapshot and checks the manifest. Incremental recomputation (2026-11-10, SID-23): IncrementalTest adds 2 Spark tests, bringing the total to 39. Ten batches through the real pipeline cover an assignment correction (UNIT-A, UNIT-B and UNIT-D recomputed: the units of the container the sensor left and of the one it names now), a pallet leaving its container (UNIT-A, UNIT-D), a specification change (every unit of the product code), a reading revision and a reading from an unassigned sensor (UNIT-B only), custody (UNIT-A, UNIT-D), an inventory change with a retry and a malformed record (UNIT-A, 1 changed event), a conflicting payload that withholds a placement (UNIT-B tombstoned and gone from the state, and the previous snapshot unchanged), a new assignment that contradicts another (UNIT-A, UNIT-D), and a configuration change that forces FULL. After every batch, all five state digests equal a full recomputation of the same canonical events, and once the readers' inventory age and flags equal a direct computation. A full Replay into an isolated namespace reproduces the incremental snapshot's digests, and a replay into the source or a used namespace is refused. The first version missed one thing a full recomputation catches: a retry at a new offset moved the canonical row's coordinates without changing its payload. The canonical row now keeps the first arrival. ScaleBenchmark measured a one-assignment correction at 4,000 units and 125,201 events: 52.8 s incremental against 106.5 s for the full replay, with Gold at 20.5 s against 75–80 s and the rest in the full canonical and Silver rebuild (detailed-design section 7). CI also runs Replay against the demo lake after the verifier. Investigation queries (2026-11-10, SID-24): QueryTest adds 3 Spark tests, bringing the total to 42. On a lake built by the real pipeline, each filter returns exactly the affected units: product, lot (LOT-2 finds UNIT-E only), shipment (SHP-DEMO finds UNIT-B and UNIT-E in BOX-B), recipient (HOSPITAL-2 finds UNIT-A and UNIT-D, but not UNIT-F, which left BOX-A before dispatch), location and outcome. Rows carry the full evidence, the latest known location with its time, age and staleness, and the shipments. A recipient sees only its units and its own shipments, a site sees its units without shipments, and requests outside a scope are refused. Paging one unit at a time while a correction is published between pages returns exactly the pinned snapshot's units and hashes; a new query then sees the correction; cursors from another query, scope, malformed or naming an uncommitted snapshot are refused. ModelTest adds 6 SHIPMENT contract cases. The demo now ships BOX-B, with the reviewed UNIT-B, to HOSPITAL-DEMO, and the verifier requires the investigator and hospital views, the refusal and consistent paging. CI found a reader defect that predates this story: the verifier polled DeltaTable.isDeltaTable, which keeps answering false for a table whose first commit another process wrote while it was polling. With slower batches the verifier now starts before the first commit, so it never saw one. Readers now check the Delta log directly, PublicationTest reproduces the foreign write, and the verifier names the checks it is still waiting on. Investigation alerts (2026-11-10, SID-25): AlertTest adds 3 Spark tests, bringing the total to 45. Seven batches through the real pipeline produce exactly the expected review items: NEW for every unit needing review at first, REVISED for all three after the assignment correction, none for a retry, a REVISED for UNIT-D only when a pallet correction recomputes UNIT-A and UNIT-D but changes only UNIT-D's assessment, WITHDRAWN (LEFT_REVIEW) when a corrected reading clears UNIT-B, NEW again when a later revision restores it, and WITHDRAWN (UNIT_REMOVED) with its last evidence when its placement is withheld. Delivery IDs are unique and the case store ends with each unit's newest item. With the pipeline relaying: a failure after Kafka accepted snapshot 1 leaves it pending and it is resent; a batch stopped after writing its items, before its manifest, relays nothing, and a drain in between sends only committed items; the case store, stopped between its two writes, then fed everything again and an older revision after a newer one, ends equal to one clean delivery with one notification per committed item. The published examples parse into the item contract unchanged, and every item the pipeline produced validates against the JSON Schema. Six mutations each fail at least one test: reporting REVISED without comparing hashes, relaying recorded snapshots again, relaying uncommitted items (caught only after the test drained between the crash and the retry), recording a snapshot before sending it, letting an older revision overwrite a case, and recording a notification twice. In Compose, the demo verifier requires every committed item in the case store once, each case at its unit's newest item, UNIT-B open for review and UNIT-A's NEW then REVISED notifications; scripts/crash-check.sh adds a third phase that halts the pipeline after Kafka accepted snapshot 2's items (the case store already had them: 4 notifications) and kills the case store; after both restart, the relay resends and the case store still holds 4 notifications for 4 committed items.

Required tests: half-open boundaries; multiple disjoint placements; nested splits; zero coverage; partial coverage; safe full coverage; exact threshold; non-finite temperature; incompatible topics; missing/overlapping specifications; simultaneous assignments; sensor calibration; equal-time inventory changes; product removal; snapshot retry; reader during partial write; new lineage replay; load/skew/backlog recovery; access-denial paths.

A story is done only with reviewable code, meaningful passing tests, updated design/runbook, documented limitations and evidence satisfying its acceptance criteria. Existing prototype coverage does not automatically close a Jira story.
